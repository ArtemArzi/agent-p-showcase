## Задача и мой вклад

Запись требует связать услугу, мастера, время и данные клиента. Между первым вопросом и подтверждением человек может передумать, выбранное время может занять другой клиент, а CRM может ответить с ошибкой. Я собирал систему, которая сохраняет контекст диалога и отделяет обсуждение записи от её фактического создания.

В основной кодовой базе реализованы:

- Telegram webhook, обработка текста и голосовых сообщений;
- оркестрация диалога и специализированные обработчики сценариев;
- получение каталога, мастеров и времени через YClients API;
- карточка выбора услуги, мастера, даты и времени;
- создание после подтверждения, просмотр, отмена и перенос записи;
- повторная проверка времени, отпечаток команды и восстановление при конфликте состояния.

## Ключевые решения

| Ситуация | Решение | Зачем |
| --- | --- | --- |
| Клиент меняет мастера или услугу | Пересогласовать связанные параметры | Старое время может перестать подходить |
| Время заняли во время диалога | Повторно проверить расписание перед созданием | Не подтверждать уже недоступное время |
| Нельзя проверить доступность | Остановить запись и предложить повторный выбор | Не превращать неопределённость в успех |
| Пришло повторное подтверждение | Сопоставить отпечаток команды | Не выполнять одинаковое действие повторно |
| Представления состояния разошлись | Явное восстановление выбора | Не продолжать с противоречивыми параметрами |

## Стек основного проекта

Python, FastAPI, LangGraph, Prefect, aiogram, Supabase/PostgreSQL, OpenAI API, YClients API, Vue и TypeScript. Разделение ответственности объяснено в [архитектуре](docs/architecture.md).

## Запустить пример за минуту

Нужен Python 3.10+; установка зависимостей не требуется.

```bash
python3 scenario_demo.py
python3 -m unittest -v
```

Первый запуск выводит шесть синтетических сценариев. Второй проверяет 11 контрактов примера, включая отказ CRM, неизвестную доступность и повтор после неясного ответа. Эти проверки относятся **только к новому примеру**, не ко всему agent_p.

## Статус и границы

Основной проект имеет реализованную кодовую базу и интеграцию с YClients. Наличие сценариев и тестов проверено по исходникам; актуальный production-прогон, масштаб использования и экономический эффект этим разбором не подтверждены. Полный путь записи нескольких услуг с реальным провайдером отдельно не проверен. Передача оператору в просмотренной версии остаётся заглушкой.

Отпечаток и заголовок Idempotency-Key в основном проекте не доказывают поддержку этого заголовка внешней CRM. Автономный пример хранит результаты только в памяти одного процесса: не моделирует конкурентные запросы, перезапуск, persistent outbox или гарантию exactly-once. Неясный результат тестовой CRM в примере требует сверки перед повтором; это отдельный учебный контракт, а не заявление о production-восстановлении agent_p.
